# Phase 0 Research: Issue Tracker MVP

**Feature**: [spec.md](./spec.md) | **Plan**: [plan.md](./plan.md) | **Date**: 2026-09-27

Every Technical Context item in the plan is resolved below; no `NEEDS CLARIFICATION` remains. Each
entry records the decision, why it was chosen, and what else was considered. Package versions are
"latest stable compatible with .NET 10" and are pinned centrally in `Directory.Packages.props`.

## R1. Runtime and language

- **Decision**: .NET 10 (LTS, supported until November 2028) with C# 14, SDK pinned in `global.json`.
- **Rationale**: Mandated by the constitution; LTS gives the longest support window for an internal
  system of record.
- **Alternatives considered**: .NET 9 (STS, support ends earlier); waiting for .NET 11 (not LTS).

## R2. UI hosting model

- **Decision**: ASP.NET Core **Blazor Web App** with the **Interactive Server** render mode applied
  globally. The ASP.NET Core Identity account pages stay **static server-rendered** (excluded with
  `[ExcludeFromInteractiveRouting]`) because they must read and write the authentication cookie.
- **Rationale**: Internal network with low latency; UI code calls application services in-process,
  so there is no public HTTP API to secure or version (a public API is out of scope); no code or data
  access logic ships to the browser; fast first load. 300 concurrent circuits fit comfortably on one
  server, matching the single-server reliability level (SC-011).
- **Alternatives considered**: Interactive WebAssembly (needs a public API layer and duplicated
  authorization; larger download); Auto mode (both costs); MVC/Razor Pages (weaker interactivity for
  boards and inline editing).
- **Consequences**: circuits need a persistent WebSocket (enable WebSockets on IIS and proxies); a
  future scale-out needs sticky sessions or a SignalR backplane service.

## R3. Component library

- **Decision**: **Microsoft Fluent UI Blazor** components for inputs, dialogs, menus, data grids, and
  comboboxes; board and backlog lists are custom components built on native HTML drag-and-drop events
  plus a keyboard "Move to" menu.
- **Rationale**: Microsoft-maintained, built with accessibility in mind (supports WCAG 2.2 AA,
  constitution VI). Building an accessible combobox, grid, and dialog from scratch is large and risky.
- **Alternatives considered**: MudBlazor (capable, but more custom accessibility work); Radzen or
  Syncfusion (commercial licensing or heavier); no library (too much bespoke accessible UI).

## R4. Solution structure and module boundaries

- **Decision**: One deployable app built from four source projects: `Upms.Domain`,
  `Upms.Application`, `Upms.Infrastructure`, `Upms.Web`. Inside each project, code is
  foldered by module: **Identity** (accounts, audit, settings), **Projects** (projects, membership),
  **Issues** (issues, labels, history, attachments), **Collaboration** (comments, watches,
  notifications, email), **Planning** (board, backlog, sprints), and **Search** (search, saved
  filters, My Work). Each module publishes a `Contracts` namespace. Architecture tests (ArchUnitNET)
  fail the build if a module touches another module's domain types or tables other than through
  those contracts.
- **Rationale**: Satisfies constitution V (one app, explicit module boundaries) with enforcement in
  CI instead of convention alone; the layering keeps domain rules free of I/O, so they can be tested
  first and fast (constitution II).
- **Alternatives considered**: one project with folders (boundaries not enforceable); a project per
  module per layer (about 24 projects, too heavy); microservices (rejected by the constitution).

## R5. Data access

- **Decision**: EF Core 10 with the SQL Server provider, a single `AppDbContext`, per-module
  `IEntityTypeConfiguration` classes, and migrations in `Upms.Infrastructure`. Application services
  use the context directly through module-scoped query and command code: no generic repositories, no
  mediator library, no object-mapping library.
- **Rationale**: The least code for a single database; EF Core supports everything required
  (rowversion, global query filters, `DateOnly`, full-text functions). Avoiding MediatR, AutoMapper,
  and FluentAssertions also avoids their 2025 move to commercial licences.
- **Alternatives considered**: Dapper (hand-written SQL for every query); repository and unit-of-work
  wrappers (duplicate what EF already provides).

## R6. Identity, sessions, and sign-in security

- **Decision**: ASP.NET Core Identity with EF Core stores and cookie authentication.
  - Password policy: minimum length 12, no composition rules (NIST 800-63B style), plus a custom
    validator rejecting passwords that contain the username (FR-004).
  - Lockout: 5 failed attempts, 15-minute lockout, enabled for all users (FR-004).
  - Temporary passwords: generated by the system (cryptographic random, 16 characters), shown once to
    the administrator, and the `MustChangePassword` flag forces a change before any other page loads.
    The guard runs both as middleware (HTTP requests) and in the router (interactive navigation).
  - Audit: a derived `SignInManager` writes sign-in success, failure, and lockout audit events
    (FR-011).
  - Revalidation: `RevalidatingServerAuthenticationStateProvider` checks the security stamp and the
    active flag every minute; deactivation and role changes rotate the security stamp, which ends
    open circuits (US6 scenario 1).
  - Idle timeout (FR-005): a `CircuitHandler` inbound-activity handler tracks the last activity on
    the server; a small JavaScript module shows the warning 2 minutes before expiry; "Stay signed in"
    calls `POST /account/keepalive` to renew the sliding cookie; at expiry the user is signed out. The
    timeout comes from organization settings (default 30 minutes).
  - SSO readiness: company SSO (OpenID Connect, e.g. Entra ID) can later be added as an external login
    linked to the same `User` records (`AspNetUserLogins`), so issue data never migrates.
- **Rationale**: Built-in, well-reviewed implementation that meets constitution III; Identity already
  hashes passwords, handles lockout, and rotates security stamps.
- **Alternatives considered**: a separate identity server such as Duende or Keycloak (extra
  infrastructure and licensing, unnecessary for a single app); Windows authentication (the user chose
  built-in accounts).

## R7. Authorization model

- **Decision**: A fallback authorization policy requires an authenticated, active user everywhere
  except the sign-in, setup, and health endpoints. **Every application-service method** starts with a
  permission check through the Projects module contract `IProjectAccess`, which reads the caller's
  organization role and project membership from the database on each call (no stale claims). A
  missing or inaccessible project or issue returns `NotFound`; a visible resource with an insufficient
  role returns `Forbidden`. UI visibility mirrors the same checks but is never relied on. The full
  role × action matrix is in [contracts/permissions.md](./contracts/permissions.md) and is tested
  exhaustively (SC-005).
- **Rationale**: In Blazor Server every UI event runs on the server, so service-level checks are the
  single enforcement point. Reading membership per call makes removal effective at once (edge case
  "Removed project member").
- **Alternatives considered**: claims-based project roles in the cookie (stale until re-sign-in);
  resource-based authorization handlers only in components (bypassable by crafted circuit calls).

## R8. First-run setup

- **Decision**: A `/setup` page creates the first Administrator. It works only while no active
  Administrator exists, and it requires a one-time setup token from configuration (`Setup:Token`,
  provided via environment variable or secret store). The first successful setup disables the page
  permanently.
- **Rationale**: FR-002; the token prevents someone else on the network from claiming a
  freshly deployed instance.
- **Alternatives considered**: a seed administrator from configuration (a password in config); a
  command-line tool (less friendly for the operations team).

## R9. Issue keys

- **Decision**: `Project.NextIssueNumber` is incremented atomically inside the issue-creation
  transaction (`UPDATE … SET NextIssueNumber += 1 OUTPUT deleted.NextIssueNumber`), and the issue
  stores `Number` and its immutable `Key` (e.g. `PAY-42`) under unique indexes.
- **Rationale**: FR-018: concurrent creations serialize on the project row, so there are no
  duplicates, and a rolled-back transaction also rolls back the counter, so numbers are never
  reused.
- **Alternatives considered**: `MAX(Number)+1` (races); SQL sequences per project (hundreds of
  sequences; gaps).

## R10. Board and backlog ordering

- **Decision**: Each issue has a `Rank` string produced by a fractional-indexing algorithm (base-62
  keys between two neighbours), stored in `varchar(64)` with a binary collation so ordinal sort
  matches. A move writes one row. A background rebalance rewrites ranks for a project if any key
  exceeds 48 characters. Board and backlog share the same rank (FR-039).
- **Rationale**: Moving a card never renumbers a whole column, so drag-and-drop stays fast at 500,000
  issues.
- **Alternatives considered**: integer positions (mass updates on every move); decimal midpoints
  (precision runs out after roughly 60 moves into the same gap).

## R11. Concurrency

- **Decision**: `rowversion` concurrency tokens on Issue, Comment, Sprint, Project, and
  OrganizationSettings. Commands carry the version the user loaded; on
  `DbUpdateConcurrencyException` the service returns `Conflict` with the current values, and the UI
  shows them next to the user's own unsaved input (FR-024, US1 scenario 9, US2 scenario 7).
- **Rationale**: Optimistic locking suits low-contention editing (constitution IV) and is native to
  EF Core and SQL Server.
- **Alternatives considered**: pessimistic locks (block other users); last-write-wins (forbidden by
  the constitution).

## R12. Change history and audit log

- **Decision**: Issue state changes only through domain methods (`ChangeStatus`, `Assign`,
  `UpdateSummary`, …). Each method appends `IssueChange` records, grouped by a `ChangeSetId` per
  action, in the same transaction. Security events go to `AuditEvent` through `IAuditLog`. Both tables
  are append-only, enforced by `INSTEAD OF UPDATE, DELETE` triggers created in migrations.
  Architecture tests assert that Issue properties have non-public setters, so no change can bypass
  the history.
- **Rationale**: FR-037, SC-004, constitution IV; explicit domain events are easy to test first and
  read clearly in history ("Status: In Progress → Done").
- **Alternatives considered**: an EF `SaveChanges` interceptor diffing all properties (automatic, but
  it loses intent and produces noise); SQL Server temporal tables (good for point-in-time, awkward for
  user-facing history with actors).

## R13. Deletion and archiving

- **Decision**: Soft delete (`IsDeleted`, `DeletedAt`, `DeletedById`) for issues and comments, with EF
  global query filters; administrators use explicit `IgnoreQueryFilters()` queries to list and restore
  deleted issues. Deleting a parent soft-deletes its sub-tasks in the same change set; deleting an Epic
  clears children's `ParentId` (recorded in their history). Projects are archived, never deleted.
  Attachment purge (FR-056) is the only permanent deletion; it removes the file content and keeps the
  metadata and audit trail.
- **Rationale**: FR-025, FR-015, FR-056, constitution IV.
- **Alternatives considered**: hard delete with an archive table (more moving parts).

## R14. Search

- **Decision**: **SQL Server Full-Text Search** indexes on `Issues(Summary, Description)` and
  `Comments(Body)`, queried through `EF.Functions.Contains` with prefix terms (`"refund*"`). Other
  filters use ordinary indexed predicates. Input matching `^[A-Z][A-Z0-9]{1,9}-\d+$` is treated as an
  issue key and opens the issue directly (FR-045). Results are ordered by `UpdatedAt DESC` by default.
  Local and CI SQL Server containers use a small custom image that adds the `mssql-server-fts` package
  ([docker/sqlserver-fts/Dockerfile](../../docker/sqlserver-fts/Dockerfile), created during
  implementation); Windows SQL Server and Azure SQL include the feature.
- **Rationale**: Meets SC-002 at 500,000 issues without new infrastructure (constitution V); `LIKE
  '%term%'` scans over 32,000-character descriptions and millions of comments would not.
- **Alternatives considered**: Elasticsearch or OpenSearch (a new cluster to run and secure); `LIKE`
  (too slow); SQL Server 2025 vector search (semantic search not required).

## R15. Formatted text and mentions

- **Decision**: Descriptions and comments are stored as Markdown. They are rendered with **Markdig**
  (raw HTML disabled) and then passed through **HtmlSanitizer** with an allowlist (headings, emphasis,
  lists, links, code, tables); links are limited to `http`, `https`, and `mailto` and get
  `rel="noopener noreferrer nofollow"`. The editor is an accessible textarea with a small formatting
  toolbar and a Preview tab. Mentions use `@username`, with suggestions limited to users who can access
  the project; unresolvable mentions stay plain text and notify no one.
- **Rationale**: FR-017, FR-033, FR-034, FR-052; two independent layers against script injection.
- **Alternatives considered**: a WYSIWYG editor storing HTML (larger attack surface, heavy JavaScript);
  plain text only (fails the formatting requirement).

## R16. Attachments

- **Decision**: File metadata lives in `Attachments`; bytes live in a separate `AttachmentContents`
  table (`varbinary(max)`) behind an `IAttachmentStore` interface. Uploads use Blazor `InputFile` with
  a 10 MB limit and are validated three ways: extension allowlist, file-signature ("magic number")
  check, and size (FR-053). OOXML documents are accepted only with their macro-free extensions
  (`.docx`, `.xlsx`, `.pptx`). Downloads go through an authenticated minimal-API endpoint that checks
  view permission and `ScanStatus = Clean`, and sends `Content-Disposition: attachment` (inline only
  for image previews), `X-Content-Type-Options: nosniff`, and a restrictive `Content-Security-Policy:
  sandbox`.
- **Rationale**: Keeping files in the same database keeps backups and restores consistent (SC-012)
  and adds no storage infrastructure (constitution V). Estimated volume: about 100,000 files at 1 MB
  average, roughly 100 GB. `IAttachmentStore` allows moving bytes to a file share or blob storage
  later without touching features.
- **Alternatives considered**: FILESTREAM (unsupported on SQL Server on Linux, which conflicts with
  the portability rule); a file share or blob storage (a second store to back up and secure).

## R17. Malware scanning

- **Decision**: A pluggable `IMalwareScanner`, with the default implementation talking to **ClamAV
  `clamd`** over TCP using its `INSTREAM` protocol (a small in-house client, no package). New uploads
  are saved with `ScanStatus = Pending`. A background worker scans them and marks them `Clean` or
  `Blocked`; `Blocked` writes a `MalwareDetected` audit event and notifies the uploader. If the
  scanner is unreachable, files stay `Pending` and the worker retries with backoff (edge case "Malware
  check unavailable"). Integration tests use the harmless EICAR test file against a ClamAV container
  (SC-010).
- **Rationale**: FR-054 needs a real scanner; ClamAV runs in a container next to the app or on a
  Windows host, keeping the app itself OS-independent. The interface allows an adapter for the
  company's own antivirus gateway (for example ICAP) later.
- **Alternatives considered**: Windows Defender through AMSI (Windows-only, which breaks portability);
  a cloud scanning API (sends internal files outside the organization); no scanning (fails FR-054).

## R18. Email notifications

- **Decision**: **MailKit** sends through the company SMTP relay, using a **transactional outbox**:
  the action that triggers an email inserts an `EmailOutboxMessage` in the same transaction, and a
  background worker delivers it with exponential backoff for up to 24 hours before marking it
  `Expired` (FR-058). Emails contain only the issue key, summary, actor, what happened, and a link
  (FR-057); they are skipped for deactivated users and for users who switched them off. Local
  development uses a Mailpit container; tests use a fake sender.
- **Rationale**: User actions never wait on the mail server; there is no lost email after a crash;
  Microsoft recommends MailKit over the legacy `SmtpClient`.
- **Alternatives considered**: sending inline during the request (slow and blocks on relay failure);
  a message broker (unnecessary infrastructure).

## R19. Background processing

- **Decision**: In-process `BackgroundService` workers (outbox sender, attachment scanner, rank
  rebalancer) poll their tables and claim rows with `UPDLOCK, READPAST` hints so they stay correct if
  a second instance is ever added.
- **Rationale**: No scheduler library or broker needed at this scale (constitution V).
- **Alternatives considered**: Hangfire or Quartz.NET (extra dependencies and tables for three simple
  loops).

## R20. In-app notifications

- **Decision**: `Notification` rows are created in the same transaction as the triggering change.
  The unread count refreshes on navigation and every 60 seconds; there is no push channel. Actors are
  never notified of their own actions (FR-036).
- **Rationale**: The spec does not require live updates; polling a single indexed count query is
  cheap.
- **Alternatives considered**: a real-time SignalR notification hub (more complexity for no required
  behavior).

## R21. Time handling

- **Decision**: All timestamps are `datetimeoffset` in UTC produced by an injected `TimeProvider`
  (deterministic in tests). Due dates and sprint dates are `date` (`DateOnly`). Users store an IANA
  time zone (default: the organization setting); the UI converts at display time.
- **Rationale**: FR-051, constitution IV; IANA IDs work on both Linux and Windows in .NET.
- **Alternatives considered**: server-local time (breaks across time zones).

## R22. Accessibility approach

- **Decision**: Fluent UI components with landmark regions and skip links. Every drag-and-drop has a
  "Move to…" menu and keyboard shortcuts (card focused, then `M`). Focus is managed after dialogs and
  moves. Automated checks use **Deque axe-core** through `Deque.AxeCore.Playwright` on every primary
  screen, plus a manual screen-reader pass (NVDA with Edge) before release.
- **Rationale**: Constitution VI, FR-050, SC-008.
- **Alternatives considered**: manual checks only (not repeatable in CI).

## R23. Observability

- **Decision**: `ILogger` with the JSON console formatter; OpenTelemetry traces and metrics
  (ASP.NET Core, EF Core, HttpClient, and custom meters for service latency, outbox backlog, and
  pending scans), exported via OTLP when configured. `/health/live` and `/health/ready` endpoints
  report the database as critical and the scanner and SMTP relay as "degraded" only. Logs record
  user, project, and issue IDs, never issue text, comments, passwords, or tokens.
- **Rationale**: Constitution "Observability" standard; degraded dependencies must not take the app
  down (edge cases).
- **Alternatives considered**: Serilog (not needed alongside built-in logging and OpenTelemetry).

## R24. Testing strategy

- **Decision**:
  - `Upms.Domain.Tests` (xUnit v3): workflow, hierarchy, keys, ranks, sprint rules, permission
    matrix logic. Written first (red-green-refactor).
  - `Upms.Application.Tests` (xUnit + Testcontainers SQL Server with full-text + Respawn):
    every application service against a real database, including concurrency, history, soft delete,
    full-text search, and the permission matrix (SC-005, SC-006).
  - `Upms.Web.Tests` (bUnit): component behavior (inline edit, conflict banner, move menu, idle
    warning).
  - `Upms.E2E.Tests` (Playwright + axe): one end-to-end journey per user story, plus
    accessibility scans (SC-008). The ClamAV scan test runs against a ClamAV container.
  - `Upms.Architecture.Tests` (ArchUnitNET): module boundaries and private setters.
  - `Upms.Performance.Tests` (opt-in category): seeded 500,000-issue database, 300 concurrent
    simulated users calling application services; asserts p95 ≤ 1 s (SC-002).
  - Test names embed the acceptance scenario they prove (`US1_AS3_…`), giving traceability from the
    spec to tests.
- **Rationale**: Constitution II and the platform testing standard.
- **Alternatives considered**: EF InMemory or SQLite for data tests (forbidden by the constitution);
  a load tool driving the browser (Blazor Server traffic is SignalR, which is hard to script; a
  service-level harness plus Playwright timings is more reliable).

## R25. Deployment, reliability, and operations

- **Decision**: One build output published two ways: a Linux container image (`Dockerfile`) and a
  framework-dependent folder for Windows Server/IIS (ASP.NET Core Hosting Bundle, WebSockets on).
  - Data protection keys are persisted in the database and protected with an X.509 certificate from
    configuration, so cookies survive restarts on both platforms.
  - Reliability (SC-011, SC-012): a single app instance with SQL Server full backups (daily),
    differential backups (every 6 hours), and transaction log backups every 15 minutes, giving an RPO
    of 1 hour or better. A restore runbook targets an RTO under 4 hours and is drilled before go-live
    and twice a year. Encryption at rest (TDE) is recommended for the database.
  - TLS is terminated at the company load balancer or at Kestrel with a certificate; HSTS is on.
- **Rationale**: Constitution portability rule; the standard reliability level needs no duplicate
  servers.
- **Alternatives considered**: an active-active cluster (only needed for the high-availability
  level, which was not chosen).

## R26. Security hardening

- **Decision**: Content Security Policy (`default-src 'self'`; scripts from self only; inline styles
  allowed for the component library); HSTS; `X-Frame-Options: DENY`; the Blazor hub rejects
  cross-origin WebSocket requests by validating the `Origin` header against `App:PublicBaseUrl`;
  ASP.NET Core rate limiting on sign-in and setup; `NuGetAudit` set to fail the build on high or
  critical advisories; secrets only from environment variables, user secrets (development), or the
  company secret store.
- **Rationale**: Constitution III; defense in depth for an internal system holding company
  information.
- **Alternatives considered**: relying on network perimeter only (insufficient against insiders or
  phishing).

## R27. Performance approach

- **Decision**: Read-side queries project straight into DTOs with `AsNoTracking`. Indexes support
  every list and filter (see [data-model.md](./data-model.md)). Lists are paginated at 50 (FR-026,
  FR-046). Board columns render with Blazor `Virtualize`, and the continuous-flow Done column is
  limited to 14 days (FR-029). A seed tool (`tools/Upms.Seed`) generates realistic volumes for the
  performance tests.
- **Rationale**: SC-002 at the stated scale.
- **Alternatives considered**: a distributed cache (unneeded at this scale; would need justification
  under constitution V).
